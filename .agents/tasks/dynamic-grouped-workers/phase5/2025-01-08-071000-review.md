## High-level view

The gateway metrics now include HTTP-level counters (`gateway_requests_total`), per-worker health gauges, circuit breaker state, cold start duration histograms, and request queue metrics. These complement the existing Phase 4 dispatch/scaling metrics without breaking them.

Worker observability is achieved through a new `WorkerMetrics` struct that emits request counts, duration histograms, config version, and reload counters. These are wired into the handler's execute path and the hot-reload loop.

Distributed tracing uses OpenTelemetry's W3C propagation. The gateway injects trace context via `otel.GetTextMapPropagator().Inject()`, and workers extract it with the corresponding `Extract()`. Custom `X-Request-Id` and `X-Trace-Id` headers are preserved for legacy compatibility.

Request queueing during cold start prevents request storms. When the dispatcher detects replicas=0, it enqueues requests instead of blocking synchronously. After `waitForReady` succeeds, the scaler drains the queue by calling back into the dispatcher's forward path.

Security hardening applies `runAsNonRoot`, `readOnlyRootFilesystem`, and `capabilities.drop: [ALL]` to the deployment template. Network policies restrict worker ingress to the engine gateway and egress to Postgres, Valkey, and the engine.

### Gateway metrics enhancement

The `GatewayMetrics` struct now includes:
- `gateway_requests_total{group,method,path,status}` for HTTP-level counting
- `gateway_request_duration_seconds{group}` histogram for end-to-end latency
- `gateway_worker_health{group,worker_id}` gauge for per-pod health
- `gateway_circuit_breaker_state{group}` gauge (0=closed, 1=half-open, 2=open)
- `gateway_cold_start_duration_seconds{group}` histogram for scale-from-zero latency
- `gateway_queue_length{group}` and `gateway_queue_timeout_total{group}` for queue observability

The existing Phase 4 metrics (`gateway_dispatch_total`, `gateway_dispatch_duration_seconds`, `gateway_worker_ready`, `gateway_worker_replicas`, `gateway_scale_operations_total`) are unchanged — no breaking changes.

The latency buckets are tuned for SLO targets (1ms to 5s for dispatch, 0.5s to 90s for cold start).

### Worker metrics

`WorkerMetrics` provides:
- `worker_requests_total{group,flow_id,status}` counter
- `worker_request_duration_seconds{group,flow_id}` histogram
- `worker_config_version{group}` gauge
- `worker_flows_loaded{group}`, `worker_jdms_loaded{group}` gauges
- `worker_connections_active{group,connection}` gauge
- `worker_reload_total{group,status}` counter

These are wired into:
- `Worker.LoadGroup()` emits config version, flow/JDM/connection counts
- `Handler.handleExecute()` emits request metrics with duration
- `Reloader.reload()` emits reload success/failure counter

### Distributed tracing

`tracing.go` provides:
- `InjectTraceContext(ctx, req)` — W3C trace context injection plus legacy headers
- `ExtractTraceContext(ctx, r)` — W3C trace context extraction
- `StartDispatchSpan`, `StartScaleSpan`, `StartClientSpan`, `StartWorkerExecuteSpan` — span creation helpers
- `TracingFields(ctx, group)` — extracts request_id, trace_id, group for structured logging

The dispatcher wraps execution in a `gateway.dispatch` span with group and flow_id attributes. The scaler wraps scale operations in `gateway.scale.*` spans. The worker handler extracts trace context from headers and starts a `worker.execute` span properly parented to the gateway span.

### Request queueing during cold start

`RequestQueue` provides per-group buffering:
- `Enqueue()` adds a request and blocks until response or timeout
- `Drain()` processes all queued requests when worker becomes ready
- `QueueLength()`, `IsQueueing()` for status checks
- `ErrQueueFull`, `ErrQueueTimeout` error sentinels

The dispatcher detects cold start via `isColdStart()` (checks if replicas == 0) and enqueues instead of blocking. The scaler's `waitForReady()` calls `drainQueue()` after the worker becomes ready, which invokes the dispatch function for each queued request.

The wiring uses `SetDispatchFunc()` on the scaler to avoid circular dependencies between Dispatcher and Scaler.

### Security hardening

The deployment template now includes:
- Pod-level: `runAsNonRoot: true`, `runAsUser: 1000`, `runAsGroup: 1000`, `fsGroup: 1000`
- Container-level: `readOnlyRootFilesystem: true`, `allowPrivilegeEscalation: false`, `capabilities.drop: [ALL]`

Tests verify the security context is rendered in generated manifests.

### Network policies

Two NetworkPolicies created:
1. `worker-isolation` — restricts worker ingress to engine pods only, egress to DNS, Postgres, engine, and Valkey
2. `engine-gateway-policy` — restricts engine ingress from ingress-nginx, workers, and Prometheus; egress to workers, Postgres, Valkey, and K8s API

The policies use label selectors (`app: flow-worker`, `app: engine`, etc.) matching the deployment templates.

### Prometheus alerting rules

Six rules created:
- `WorkerGroupDown` — critical, triggers when all workers for a group are down for 1m
- `WorkerHighErrorRate` — warning, triggers when error rate > 10% for 5m
- `WorkerColdStartSlow` — warning, triggers when p95 cold start > 10s for 5m
- `GatewayCircuitOpen` — critical, triggers when circuit breaker state == 2 (open) for 1m
- `GatewayQueueBacklog` — warning, triggers when queue length > 100 for 2m
- `GatewayHighLatency` — warning, triggers when p99 dispatch latency > 2s for 5m

All rules include runbook URLs for ops documentation.
