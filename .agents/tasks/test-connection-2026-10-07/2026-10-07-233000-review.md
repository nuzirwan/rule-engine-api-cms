# Test Connection Feature for Database/Service Connections

This change adds the ability to test database and service connections before syncing them to the engine. The feature spans three layers: an engine endpoint (`POST /admin/connections/test`), a CMS proxy controller (`POST /rule-engine/connections/test`), and an admin UI modal (`TestConnectionModal`). The design passes the password in the request body for ephemeral use — it is never stored. The secret flows through `connect.WithSecret(ctx, secret)` on the engine side, consistent with how the existing connector drivers expect credentials.

**Watch for:** Nothing blocking. The implementation follows established patterns, all tests pass, and secret handling is appropriately ephemeral.

**Verdict**: APPROVED

## High-level view

The engine endpoint uses `ConnectorLookup` to find the connector factory by type, builds a temporary `ConnectionDef`, injects the secret via context, opens the client, and runs a ping operation. Failures at open or ping return `{success: false, error}` with HTTP 200; validation errors (missing type, unknown type) return 400.

The CMS proxy controller validates the request body, calls `AdminClient.testConnection()`, and classifies engine errors per the §5.5 table (5xx → 503 recoverable, 4xx → echo status). The types `TestConnectionRequest` and `TestConnectionResponse` are added to `cms/types/engine.ts`.

The admin UI adds a `ConnectionsPage` that lists connections and a `TestConnectionModal` that displays read-only settings, accepts a password, and calls the test endpoint. The password field is cleared on modal close and the value is never persisted.

## Engine endpoint: ephemeral test via connector lookup

The handler introduces `ConnectorLookup`, an optional interface the registry implements to expose connector factories by type. This avoids going through the defs table for a connection that doesn't exist yet. The endpoint:

1. Validates `type` is present (returns 400 if missing)
2. Looks up the connector (returns 400 for unknown type)
3. Builds a temporary `ConnectionDef{Key: "_test", Type, Settings}`
4. Injects secret via `connect.WithSecret(ctx, connect.NewPlainSecret(req.Secret))`
5. Opens the client
6. Executes `{Kind: "ping"}`
7. Returns `{success: true/false, message/error}`

Both `registry` and `registryV2` implement the new `Connector(typ string)` method, so the endpoint works regardless of which pool implementation is active.

`NewPlainSecret` is added to wrap a plaintext string in a redacting `Secret`. The `String()` method still returns `***`, so the value won't leak into logs.

## CMS proxy: validation and error classification

The controller validates all three required fields (`type`, `settings`, `secret`) before calling the engine. Missing or invalid fields return 400 with a descriptive error.

Error classification follows the existing pattern: 5xx or transport errors → 503 with `recoverable: true`, 4xx → echo the engine status with `recoverable: false`. This lets the UI distinguish between "try again later" and "fix your input."

## Admin UI: ConnectionsPage and TestConnectionModal

`ConnectionsPage` lists connections from `/api/connections?populate=settings`, displaying key, type badge, host/endpoint, and secret ref. The "Test" button opens `TestConnectionModal`.

The modal shows connection settings as read-only fields (extracted via `extractDisplaySettings` helper that handles both flat objects and Strapi dynamic zones). A password input field with hint "The password is used only for this test and is not stored" prompts for the credential. On submit, it POSTs to `/rule-engine/connections/test` and displays a success/failure badge.

State is reset when the modal opens (password cleared, result cleared), so stale results don't persist across tests.

## Test coverage

**Engine tests** (`admin_test.go`): 5 scenarios using mock `fakeConnector` and `fakeClient`:
- Missing type → 400
- Unknown type → 400
- Successful connection → 200 with `success: true`
- Open fails → 200 with `success: false, error`
- Ping fails → 200 with `success: false, error`

**CMS tests** (`connection-test.test.ts`): 8 scenarios with nock:
- Success → 200 with `success: true`
- Engine returns `success: false` → passes through
- Missing type/settings/secret → 400
- Engine 5xx → 503 recoverable
- Engine 4xx → echo status non-recoverable
- Missing config → 503

**UI tests** (`TestConnectionModal.test.ts`): smoke tests for props interface, `extractDisplaySettings` helper, and request body shape. These don't render the component (would need full Strapi admin environment) but verify the type contracts.

**Not tested:** actual network connection to a real database. The tests mock the connector layer, which is appropriate for unit tests.

## Route registration

Engine: `mux.Handle("POST /admin/connections/test", h(a.testConnection))` in `admin.go`.

CMS: `{ method: 'POST', path: '/connections/test', handler: 'connection-test.testConnection' }` in `routes/index.ts`, controller registered as `'connection-test': connectionTestController` in `server/src/index.ts`.

Admin UI: `/connections` route added to plugin routes, lazy-loading `ConnectionsPage`.
